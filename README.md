# E-Commerce Order Fulfillment Operations Analysis

## Project Overview

This project analyzes **e-commerce order fulfillment operations** to identify operational inefficiencies, customer dissatisfaction drivers, and refund risk patterns.

It is a **full analytics pipeline**: a seeded data generator + validation suite, an ETL and feature-engineering layer (Python/pandas), a SQL analysis layer (PostgreSQL), exploratory notebooks, a trained refund-prediction model, and an interactive Streamlit dashboard.

The analysis focuses on how **delivery delays, service ratings, platforms, and product categories** drive refunds — and whether a learned model can beat an explainable rule-based baseline at scoring refund risk.

---

## Business Problem

E-commerce platforms frequently face operational issues such as:

* Late deliveries
* Poor service experience
* High refund rates
* Inconsistent performance across platforms and categories

Refunds are **costly consequences**, not random events.

This project answers:

* Where are delivery delays happening?
* Which platforms and product categories are operationally weak?
* How do service ratings and delivery delays relate to refunds?
* Can we score refund risk at the order level — with both **explainable rules** and a **trained model**?

## Dataset

The dataset is **synthetic but realistic**, generated by a seeded, reproducible script so the analysis is fully auditable.

| | |
|---|---|
| **Generator** | `scripts/generate_data.py` (seeded, reproducible) |
| **Validation** | `scripts/validate_data.py` (21 checks, fails if determinism returns) |
| **Size** | 100,000 orders, 2,302 customers |
| **Time range** | 2024-11-01 → 2025-01-31 (evening/weekend demand weighting) |
| **Platforms** | Blinkit, JioMart, Swiggy Instamart |
| **Categories** | Grocery, Dairy, Beverages, Snacks, Personal Care, Fruits & Vegetables |

The generator deliberately produces **probabilistic** relationships — delay is derived from promised-vs-actual delivery minutes, and refunds depend on rating *and* delay *and* category — so the analysis and the model must genuinely *learn* from the data rather than re-discover pre-baked rules. The validator enforces this (see `docs/validation_report.md`).

### Key Fields

* `order_id`, `customer_id`, `platform`
* `order_date_time` — real timestamps (the original dataset shipped a corrupted `Order Date & Time`)
* `promised_delivery_minutes`, `actual_delivery_minutes` — used to derive delay
* `product_category`, `order_value_inr`, `items_count`
* `service_rating` (1–5), `delivery_delay` (Yes/No), `refund_requested` (Yes/No)

Full column documentation in [`docs/data_dictionary.md`](docs/data_dictionary.md).

## Analysis Approach

Two complementary layers on the same underlying table:

1. **Python pipeline** (primary): `src/etl.py` → `src/features.py` → `src/model.py`
2. **SQL layer** (PostgreSQL): `SQL/schema.sql` defines the `orders` table; the analysis queries reproduce the same numbers as the notebooks.

Everything is reproducible: the generator is seeded, the notebooks are executed with outputs committed, and every numeric claim below can be traced to a notebook cell or a query.

## Key Analyses

### 1. Data Overview — [`notebooks/01`](notebooks/01_data_overview.ipynb) · [`SQL/data_overview.sql`](SQL/data_overview.sql)

* 100,000 orders, 2,302 distinct customers, 3 platforms, 6 categories
* All timestamps parse as real datetimes (the original data had a corrupted date column)
* Avg delivery 25.2 min, avg order value ₹503

**Purpose:** validate data before drawing conclusions.

---

### 2. Delivery Delay Analysis — [`notebooks/02`](notebooks/02_delay_analysis.ipynb) · [`SQL/delivery_delay_analysis.sql`](SQL/delivery_delay_analysis.sql)

**Overall delay rate is 13.24%** (13,245 of 100,000 orders).

**Delay by platform:**

| Platform | Delay rate |
|---|---|
| JioMart | 13.93% |
| Swiggy Instamart | 13.14% |
| Blinkit | 12.66% |

**Insight:** the platform spread is real but modest (~1.3 points). The bigger operational signal is by **category** — fresh/high-SLA goods are much more fragile.

---

### 3. Product Category Delay Analysis — [`notebooks/02`](notebooks/02_delay_analysis.ipynb) · [`SQL/category_delay_analysis.sql`](SQL/category_delay_analysis.sql)

| Category | Delay rate |
|---|---|
| Fruits & Vegetables | 18.14% |
| Personal Care | 15.84% |
| Snacks | 12.52% |
| Beverages | 12.15% |
| Dairy | 11.28% |
| Grocery | 9.51% |

**Insight:** Fruits & Vegetables is the most fragile (18.1%), while **Grocery is the most reliable (9.5%)** — the opposite of a common assumption. Higher-SLA, perishable categories carry the most delay risk.

---

### 4. Refund Behavior Analysis — [`notebooks/03`](notebooks/03_refund_analysis.ipynb) · [`SQL/refund_analysis.sql`](SQL/refund_analysis.sql)

**Overall refund rate is 18.75%** (18,751 orders).

**Refund rate by service rating:**

| Rating | Refund rate |
|---|---|
| 1 | 79.1% |
| 2 | 58.4% |
| 3 | 18.0% |
| 4 | 6.7% |
| 5 | 2.2% |

**Refund rate by delivery status:**

| Status | Refund rate |
|---|---|
| Delayed | 46.8% |
| On time | 14.5% |

**Insight:** service rating is the strongest single driver — but **not deterministic** (rating 1 refunds 79%, not 100%). Delivery delay matters too: delayed orders refund at **3.2×** the rate of on-time orders. Both rating and delay are independent, learnable signals.

---

### 5. Refund Risk Scoring — [`notebooks/05`](notebooks/05_model_evaluation.ipynb) · [`src/model.py`](src/model.py) · [`SQL/refund_risk_score.sql`](SQL/refund_risk_score.sql)

Two approaches to score refund risk at the order level:

**A. Rule-based baseline** (explainable, SQL): a hand-weighted score using Service Rating (60%), Delivery Delay (30%), Product Category (10%). Weights are explicit and business-driven.

**B. Trained models** (Python): logistic regression and random forest, with a **stratified 80/20 train/test split and 5-fold cross-validation**.

**Results on the same held-out test set (20,000 rows):**

| Model | ROC-AUC | CV AUC | F1 | Precision | Recall |
|---|---|---|---|---|---|
| Logistic regression | **0.839** | 0.837 ± 0.003 | 0.546 | 0.436 | 0.729 |
| Random forest | 0.835 | 0.832 ± 0.003 | **0.589** | 0.570 | 0.609 |
| Rule-based baseline (SQL) | 0.828 | — | 0.589 | 0.551 | 0.633 |

**Insight:** the trained logistic regression **beats the explainable rule-based baseline** (AUC 0.839 vs 0.828) on the same rows — a learned model adds signal beyond the hand-tuned rules. Feature importance confirms `service_rating` dominates (56%), matching the baseline's 60% weight, with `minutes_late`, `order_value`, and `is_delayed` as the next drivers. The saved model powers the dashboard's top-risk order view.

## Reproduce the pipeline

```bash
pip install -r requirements.txt

python scripts/generate_data.py     # 1. generate data
python scripts/validate_data.py     # 2. validate (must PASS 21/21)
python -m src.etl                   # 3. clean -> data/processed/orders_clean.csv
python -m src.features              # 4. features -> data/processed/features.csv
python -m src.model                 # 5. train/evaluate -> models/
python scripts/build_notebooks.py   # 6. rebuild notebooks
streamlit run dashboard/app.py      # 7. dashboard
```

The SQL layer can be run separately: create the table from `SQL/schema.sql`, `\copy` the clean CSV, then run the queries.

## Limitations

* Dataset is **synthetic** (seeded generator) — relationships are realistic but not measured from a real retailer
* External factors (weather, staffing, supply chain) are not modeled
* The SQL layer was verified by cross-checking query logic against the same computations in pandas; it was **not executed against a live PostgreSQL instance** in this environment
